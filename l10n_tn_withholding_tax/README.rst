This module adds Tunisian withholding tax (*retenue à la source*)
handling on bill payments.

It does **not** create any journal or rule of its own. Instead, it lets
you flag bank journals as withholding tax journals, each with its own
rate, and define **Withholding Rules** that link products to one of
these journals, or apply based only on a minimum invoice total when no
products are selected.

When you register a payment on a bill with an applicable rule, the
payment wizard:

- shows the applicable withholding taxes and the amount to withhold for
  each one;
- hides the withholding tax journals that do not apply to the bill;
- fills in the withholding amount when you select one of the applicable
  journals.

The withholding amount is computed on the bill total, taxes included,
and is recorded as a payment in the withholding tax journal. Once a
withholding tax has been paid on a bill, it is no longer proposed for
that bill.

Installation
============

This addon is incompatible with Odoo's native **Withholding Tax on
Payment** (``l10n_account_withholding_tax``). Only one of these addons
can be installed in a database, including databases with multiple
companies. Odoo blocks installation when the other addon is already
installed.

Configuration
=============

This module does not create any journal or rule. You set them up in two
steps.

**Withholding tax journals**

1. Go to *Accounting > Configuration > Journals*.
2. Create (or open) a journal of type **Bank** for the withholding rate.
   The same journal may serve customer and supplier withholding.
3. Tick **Withholding tax journal**, next to the journal type.
4. In **Withholding Tax**, enter the rate as a percentage, for example
   ``1.5`` for 1.5%.
5. Configure fiscal accounts on the payment methods in Odoo's standard
   **Incoming Payments** and **Outgoing Payments** tabs. Incoming
   payments use the customer withholding account; outgoing payments use
   the supplier withholding account. There is no additional account
   field on the journal.

Separate journals for customer and supplier withholding are optional.
Use the rule's **Document Type** to restrict a rule to customer invoices
or vendor bills.

**Withholding rules**

1. Go to *Accounting > Configuration > Withholding Rules*.
2. Create a rule and fill in:

   - **Article**: the products the rule applies to. Leave empty to apply
     the rule to any invoice meeting the minimum amount.
   - **Description**: a short explanation of the rule.
   - **Document Type**: **Customer Invoice** (``out_invoice``) or
     **Vendor Bill** (``in_invoice``). Leave empty to apply to both. The
     same journal may be used by rules for either document type.
   - **Amount**: the minimum bill total (taxes included) from which the
     withholding applies. The threshold is inclusive. Use 0 for no
     minimum. This amount cannot be negative.
   - **Withholding Tax Journal**: the journal holding the rate to apply.
     Only journals with **Journal includes Withholding Tax** ticked can
     be selected.

Product rules are filtered by company, document type and minimum amount
before selecting the highest applicable threshold (then the lowest rule
ID in case of a tie). Rules without products follow the same
compatibility checks. Alerts, available journals and invoice allocation
proposals use this selection.

**Accounting reference**

Use Odoo's standard outstanding receipt/payment account on each payment
method. A shared journal can use different accounts for incoming and
outgoing payments:

+------------------+----------------+----------------+----------------+
| Withholding flow | Payment method | Example tax    | Withholding    |
|                  |                | account        | entry          |
+==================+================+================+================+
| Customer invoice | Inbound        | 434100,        | Debit tax      |
|                  |                | withholding    | receivable,    |
|                  |                | suffered       | credit the     |
|                  |                |                | invoice's      |
|                  |                |                | customer       |
|                  |                |                | account        |
+------------------+----------------+----------------+----------------+
| Vendor bill      | Outbound       | 432000,        | Debit the      |
|                  |                | withholding    | invoice's      |
|                  |                | owed to the    | supplier       |
|                  |                | State          | account,       |
|                  |                |                | credit tax     |
|                  |                |                | payable        |
+------------------+----------------+----------------+----------------+

Use dedicated tax accounts, separate from the customer/supplier accounts
and bank accounts. Configure account numbers according to the company's
chart of accounts; these examples are not enforced. Odoo's Tunisian
chart supplies both 432 and 4341 as Current Liabilities
(``liability_current``), without reconciliation enabled. The module
accepts Current Assets (``asset_current``) and Current Liabilities for
either flow, without requiring reconciliation on the fiscal account. The
payment direction determines the debit/credit entry. Invoice counterpart
lines are still reconciled on their customer/supplier account. Account
types still affect financial report classification; accepting an account
does not verify or correct its presentation in those reports.

The journal's default bank account is not the tax account: withholding
must use its selected payment method's fiscal account, for the actual
payment direction.

A withholding journal must have type **Bank** and a valid rate. A
configured payment method account must be active, available to the
journal's company and of type Current Assets or Current Liabilities. It
must differ from the journal's default bank account and the company's
transfer account. A forced account currency must also match the payment
currency.

The rate is stored as a fraction: ``0 < rate <= 1``, where ``0.015``
means 1.5% and ``1`` means 100%. The journal form displays and accepts
percentages.

You may save a journal while its payment method account is still empty,
to finish configuration afterward. Creating or posting a withholding
payment requires an explicit fiscal account on the selected method.
Direct ORM calls and forced journal entry generation follow the same
rule; the payment's actual account and generated entry must match that
configured account. Withholding payments cannot fall back to a normal
outstanding or transfer account. Regular bank/cash payments keep Odoo's
standard behavior.

Configuration remains editable as long as it is valid. The module does
not freeze the journal or its accounts after a payment has been posted.
Changing the rate or payment method account affects future payments
without rewriting existing journal entries. Changing a journal's
withholding flag also changes the withholding classification of payments
linked to that journal.

For a gross invoice of 2,000 and a withholding of 30, register a
withholding payment of 30 and a bank payment of 1,970. Reconcile both
payment counterpart lines with the invoice. The invoice total stays
2,000 and its residual becomes zero; only the net payment affects the
bank or its normal outstanding account.

Certificate confirmation changes the workflow and records the user and
date. It must not change accounts, debit/credit amounts, residuals or
reconciliations, or create another journal entry. The tax
receivable/payable balance remains after confirmation; its subsequent
tax settlement is a separate operation. On a non-reconcilable fiscal
account, follow this balance in the general ledger, rather than using
the line's residual amount.

Use the payment's reset, cancel or reject actions to clear certificate
confirmation and its audit fields. Direct ORM state changes that leave
confirmation on a draft, canceled or rejected withholding payment are
refused.

New withholding payments are supported only for customer receipts and
supplier payments. Customer refunds and supplier reimbursements use
regular bank/cash payments, without new withholding. This also applies
to direct ORM creation or updates, including a refund document linked to
an otherwise normal payment. Reversing or settling the tax balance of an
earlier withholding is a separate operation, outside this workflow.

The certificate confirmation action is available to accounting users
with write access to the payment and a posted journal entry. It records
the current user and server date, and checks every payment in a batch
before updating any certificate. Direct ORM updates are allowed under
standard access rights when the certificate, date and user are
consistent and the withholding payment has a posted journal entry. Clear
all three fields together when resetting through the ORM; the standard
reset, cancel and reject actions do this automatically.

Usage
=====

Once the journals and rules are configured (see *Configuration*),
withholding tax is handled from the payment wizard.

Withholding applies only when both the invoice company and invoice
partner have Tunisia as their country. A missing country makes the
document ineligible. Withholding journals and alerts are not offered for
ineligible documents. Direct payment creation and confirmation enforce
the same country restriction.

One receipt for several invoices
--------------------------------

Select several invoices for the same customer and click **Pay**. Enable
**Withholding Tax Applicable**, then choose **Keep Unpaid** or
**Register Withholding Payment**.

The checkbox is shown only when several invoices are selected and at
least one has an applicable withholding rule. It is hidden when none of
the selected invoices meets the Tunisia country restriction or matches a
withholding rule.

The allocation table shows each invoice's remaining balance, applicable
withholding journals, calculated withholding amount, and cash
allocation. Different invoices can use different journals or several
journals. Edit the selected journals and cash allocations as needed;
withholding amounts are calculated from each journal's rate and the
invoice's original total, rounded per journal in the invoice currency.

Changing the bank/cash amount fills each invoice's balance after
withholding in allocation order before moving to the next invoice. Once
the cash is exhausted, later invoices receive no cash allocation. Each
invoice's withholding stays reserved. Editing cash allocations directly
updates the bank/cash total while preserving the manual distribution. An
amount above the total net balance keeps the existing allocations and
displays a warning; it cannot consume withholding.

Exactly one bank/cash payment is created for the amount received. Its
reconciliation follows the cash allocation of each invoice:

- **Keep Unpaid** leaves the withholding amount outstanding on each
  invoice. No withholding payment is created.
- **Register Withholding Payment** additionally creates one pending
  withholding payment per invoice/journal. Certificate confirmation
  remains a separate step.

A warning shows differences from the suggested net total. Partial
payments are allowed when the edited cash allocations add up to the
bank/cash amount. Confirmation is blocked for incompatible journals,
stale balances, negative or excess allocations, or cash totals that do
not match the payment. Differences are never written off automatically.

Allocation mode supports posted customer invoices or vendor bills in the
company currency, for one partner, company and receivable/payable
account. Credit notes and foreign currencies use the standard payment
flow. Existing withholding payments are excluded from the suggested
withholding journals to avoid duplicates.

Individual withholding payments
-------------------------------

1. Open a posted vendor bill that meets a withholding rule's conditions,
   and click **Pay**.
2. At the top of the wizard, a message lists the applicable withholding
   taxes, with the journal and the amount to withhold for each one.
3. In **Journal**, select the withholding tax journal. The **Amount** is
   filled in automatically with the withholding amount.
4. Click **Create Payment**.
5. Pay the rest of the bill as usual with your bank journal.

A rule applies when the bill total is equal to or higher than the rule's
**Amount** and, if products are selected, the bill contains one of them.
Rules without products also apply to invoice lines without a product.
Amount-only and matching product rules can both apply. Withholding tax
journals that do not match an applicable rule are not offered in the
**Journal** field.

Once the withholding tax has been paid, its journal is no longer offered
for that bill and the rule no longer appears in the wizard.

Invoice report with payments
----------------------------

When printing an invoice with payments, withholding payments appear
first, labelled with their journal name (for example **RS 1.5%**), with
the reconciled amount in the invoice currency. Other payments keep their
usual labels, dates and relative order. The invoice balance and
accounting entries are unchanged.

Certificate confirmation
------------------------

Withholding payments remain **In Process** until the certificate is
confirmed. The invoice or bill balance is reduced immediately, but a
fully settled invoice or bill remains **In Payment** while its
withholding certificate is pending.

- Open **Customers > Incoming Withholding Payments** to track received
  withholding. Open a payment and click **Validate Reception** after
  receiving its certificate.
- Open **Vendors > Outgoing Withholding Payments** to track issued
  withholding. Open a payment and click **Confirm Certificate Delivery**
  after delivering its certificate.

Both menus offer kanban and list views, with filters by state, partner,
journal, date and company. Confirmation records the accounting user and
date, marks the payment **Paid**, and updates the invoice or bill when
all payments are matched. Confirmation does not create another journal
entry. Resetting, canceling or rejecting a payment clears its
confirmation. Pending withholding payments still prevent duplicate
registration; canceled payments no longer block the rule.

On upgrade, existing **Paid** withholding payments are treated as
confirmed. Their confirmation user and date stay empty because no
historical certificate confirmation was recorded.
